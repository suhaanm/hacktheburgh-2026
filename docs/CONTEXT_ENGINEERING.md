### 1.3 Findings, with evidence

1. **Chained computer use cost the square of the conversation length; the shipped default no longer does.** *Measured live* (AGENT-CORE, `evals/agentic/ITERATIONS.md`): the chained thread used 211,852 input tokens over 25 calls (about 8.5k per call and growing with the step); the stateless loop that replaced it used 74,548 over 27 steps, 2.76k per step, flat (n = 1, in-sample). *Modelled* to 150 steps at a frame cost calibrated on that live run (`evals/context/token_growth.py`): the unrestarted chain would be 285.7k tokens at step 150 against 2.8k for the library prompt, 101 times (21.6M cumulative against 0.42M, 51.6 times; 13.9 times after an assumed 0.25 price for cached tokens), and the request sets `truncation: "auto"` (*code*, `audit_probes.json`), which per the provider's documentation drops the oldest items when the window fills, and the oldest items are the goal and the fact-handle list (a documented behaviour I did not test; a risk, not a failure). A chain restarted every 4 steps (`context_reset_every=4`, AGENT-CORE's first fix) would be a 2.6k to 8.6k sawtooth, 0.85M cumulative, twice the stateless cost. **Status: closed on the default path** (`stateless=True`); the numbers stay as the case for never going back, and because the benefits flow was never the worst case (each navigator is one calculator) while a single long desktop or overnight conversation would have been.
2. **The refusal feedback never reached the model in a chained segment; in the stateless default it does.** *Code, confirmed by a probe with a fake client* (`evals/context/audit_probes.py`, run against the chained path): after a refused action the chained request is `[computer_call_output]` and contains neither the goal, the task state nor the NOTE. In the stateless loop every request carries the goal, the working memory and the NOTE, so the refusal reason is delivered. **Status: closed on the default path.** It stays open for anyone who sets `stateless=False`.
3. **The text history forgot which facts were entered, and the first task state was run-wide.** *Modelled with the real functions*: a handle step is stored as `{"kind": "type", "handle": ..., "ok": true}` with no `args`, and both providers' `_history_text` printed `type {} -> ok` (the prompt could not name an entered handle in **142 of 150 steps**). MODELS made both functions print the handle at about 18:34 (94 of 150: only handles typed more than 12 steps ago are missing); AGENT-CORE's loop now builds a `WorkingMemory` whose entered handles are page-scoped (`set_page` on a change of URL path), which closes the stale "already typed" case after a 503 and Back (modelled: 0 steps cannot name an entered handle). **Status: closed on the default path.**
4. **A resume or an escalation starts over.** *Code* and the REQ-7 plan's known flaws. Tier 3 now holds its state in `WorkingMemory` (AGENT-CORE), and the runtime child writes a typed `TaskState` (completed phases, pending phase, last 6 steps, per-tool rolling summary, readings with age and source) to `data/runs/<run>/children/<cid>.task.json` after every step (AGENT-RUNTIME, ids and counts only, atomic, round-trip tested). **Not built yet**: a restart-resume flow in either (the runtime's state is continued in memory by a yield and resume, not across a process restart), `WorkingMemory.snapshot()` wired into AGENT-CORE's LH-2 checkpoint, and carrying the entered and verified state across a tier-1 to tier-2 to tier-3 escalation when the page is kept (each tier still starts with an empty history; `already_set_on_this_page` is rebuilt from the page).
5. **Duplicated and diluting context at tier 2.** *Measured, calls*: 641 input tokens per live call on clean runs and 1147 on layout-v2 and glitch runs (n = 494 live calls, `agent_live_runs.json`). By construction every step re-sends the full element list, the 241-token parameter glossary and the 266-token tool help, and the quarantined reader re-reads the whole visible page text on every step when `page_state` is on, although typing into a field does not change `innerText`. The reader already returns a digest of its input, so a memo keyed on it is safe. The fixture run in 1.6 measured it: 12 or more of the 14 to 17 reader calls per calculator re-read a page text already read. **Status: the glossary and tool-help placement is fixed (AGENT-CORE applied `tier2_messages`); the reader memo is open.**
6. **No prefix can be cached at all, and the tier-2 prompt would not be stable if it could.** *Measured (static)* (`audit_static.json`): the largest stable prefix in the product is the tier-3 instructions plus goal and facts (721 tokens), then tier 2 at about 740 (system 100, tool help 266, parameter glossary 241, goal about 130), the runtime children at 340 to 585 plus instructions, evidence at 476. The meter's cache minimum is 1024 (an assumption, both vendors). In tier 2 the tool help sits **after** the volatile page observation and the line "N actions taken" is a counter in the first lines, so consecutive prompts share only the system message and the goal: **272 tokens, 20 percent of the prompt** (synthetic 14-element page through the real prompt builder, `evals/context/ablations.py`). The ordering rule is cheap to adopt and costs nothing; the saving is small until a prefix passes the minimum. **Status: fixed for tier 2** (AGENT-CORE applied the patch; 732 to 734 shared tokens measured through the real loop, 1.6).
7. **No shared freshness rule.** Three separate limits exist: the pipeline's 30 s observation age (`max_observation_age_s`), Cue's 20 s grounding TTL (and now a table in `cue/freshness.py`), and the Live frame cadence of at least 5 s. The glance, the hazard reading, the calendar week, git habits and briefing cards have no age rule in any prompt path, and no path tells a model what it does not know.
8. **The memory file is in no model prompt.** *Code* (grep over agent, engine and desktop): the memory file is read by rules and the coach; no planner, reader or computer-use prompt receives a line of it, keyed or whole. The claim that the system "adapts to the worker" therefore rests on code paths only. When it is added, the failure to avoid is a whole-file dump; `context/retrieval.py` does keyed retrieval.
9. **Token accounting is an estimate with no sections.** *Code*: the runtime budgets tokens at characters / 4 and counts a child's tokens from that, never from provider usage; the models meter recorded totals per call with no breakdown, so a cost could not be attributed to goal, history, page or frame. MODELS added a `call_context(manifest)` hook with section counts, cached tokens and `ctx_estimate_error` at about 18:34; no caller passes a manifest yet.
10. **Provider-side retention of computer-use frames.** *Code, confirmed by the probe on the chained path*: the computer-use request did not set `store`, so the vendor default applied, and chaining requires it. MODELS added `store=False` for the stateless mode (about 18:34) and AGENT-CORE's loop now passes it on every tier-3 request. **Status: closed on the default tier-3 path**; the chained path and the other call sites (reader, planner) are unchanged.

## 2. Rules (what "correct context" means here)

1. **Typed first.** A prompt body is ids, enums and numbers that code built. Free words come from only two places: the worker (memory lines, the goal they typed) and the quarantined reader's schema-checked fields. A summary of earlier steps is a template over typed counters, never model prose.
2. **Trust by audience, enforced when the prompt is assembled.** The planner, the checker and the computer-use model never receive raw untrusted text; the reader receives untrusted text and no worker memory; the vision call receives code text and a frame. Violations raise.
3. **Stable first, volatile last.** Instructions, the goal and the fact-handle block, tool help and glossaries come first and are byte-identical from step to step (no counters, no clocks); what changes comes after; the one action asked for comes last.
4. **Bounded.** Every section can carry a token budget and the whole prompt a total. The truncation order is fixed (section 3). Nothing is cut inside an item, so a number is never cut; the model is told when something was left out.
5. **A long run carries code-held state.** The task state is the source of truth after a resume, a restart or a provider-thread reset: goal, handles on offer, postconditions code verified, handles entered on the current page, page state, open problems, what is pending. The last K steps are verbatim; older steps are a template over counts.
6. **One frame, maybe one thumbnail.** The latest screen at full size, at most one small previous thumbnail, a code-measured "did the screen change" sentence; older frames are dropped and never stored by this layer.
7. **Keyed, capped retrieval from the worker's memory.** By role, skill id, step id and routine id; never the whole file; at most 6 lines.
8. **Fresh or named.** An input older than its limit is dropped and named under "not available right now"; an input that is missing is named; neither is silently defaulted.
9. **Measured.** Every assembled prompt has a metadata-only manifest (section names, estimated tokens, dropped counts, stale and missing names, a 12-hex hash of the stable prefix) for the meter and the ledger; the provider's usage fields stay the truth and the report shows estimate-vs-actual error.

None of this changes the SafetyPipeline, fact handles, the quarantined reader or the egress guard. The library cannot send anything, has no model client and no network import, and refuses by construction to put raw untrusted text where the planner reads.

**Audiences.** planner and checker: code, worker, and untrusted only when `checked` (the reader's output); computer_use: code and worker; reader: untrusted and code, never worker; vision: code.

**Truncation order** (documented in `packet.py`, tested): 1. stale and missing inputs are removed first and named in `unknowns`; 2. `required` sections (task spec, safety rules, the current step, `unknowns`, the task state) are never dropped or trimmed; 3. a section over its own budget loses whole items (the oldest for histories, the last for ranked lists), and an item larger than its section's budget is dropped whole; 4. while the total is over budget, whole items go from the lowest-priority section first (volatile before stable, later order first); 5. a section that lost items says how many; 6. if the required sections alone exceed the budget they are kept and the manifest says `required_over_budget`.

**Freshness table** (seconds): p_stuck 6, snapshot 60, grounding 20, glance 60, input_rhythm 10, worker_state 10, meeting_state 120, hazard_reading 30, page_observation 30 (as `SecurityConfig.max_observation_age_s`), briefing_card 3600, ledger_summary 86400, calendar_week 604800, git_habits 1209600, skill_state 7776000; no limit but must exist: progress, memory_line, task_state. A reading carries `t`, the time the producer took it.

## 6. What is not claimed, and what is open

- No live-model result. The chained-versus-stateless success rate, the effect of the dropped refusal note on completion, and the provider's truncation behaviour are untested.
- Token counts are estimates (3.6 characters per token, 1150 per frame); the error against provider usage is to be reported by the meter (MODELS records `ctx_estimate_error`), not assumed small. The default frame constant (1150) comes from `detail: auto` vision calls and under-counts the OpenAI computer-use path by about 27 percent (the `openai_cu` profile, 1860, is calibrated on one live run, n = 1); MODELS' `ctx_estimate_error` will say how wrong either is on every later call.
- The `checked` flag on an untrusted section is the producer's attestation. The library cannot verify that fields came through the quarantined reader; the SafetyPipeline remains the authority and its raw-text leak check still runs.
- The cache-adjusted costs use an assumed cached-input price factor of 0.25 (the meter's default).
- The memory file is not yet in any prompt; retrieval is built and tested, not adopted.
- Section 1.7 is filled from the owners' `CTX-AUDIT` lines as the lead collects them.
