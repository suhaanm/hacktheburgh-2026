## 0. Summary

1. **Neither project does what ours does under the conditions ours does it.** Clicky (the app) points at things; it never clicks. Clicky's Windows fork has a plugin that executes single actions on request from an outside agent, with no loop and no multi-step task in the repo. Sentient OS does run an autonomous multi-step loop on real apps, but the loop, the context handling and the tool schemas live inside two closed or external pieces (the Codex command-line agent and a vendor-signed helper app). The repo holds no task-completion measurement, so it shows no evidence that it avoids our failures.
2. **The owner's belief ("they do not face our problems") is untested, not confirmed.** Sentient's success signal is the model's own final claim after a clean process exit. It has no oracle like our figure recomputation, so a wrong figure with a confident Done would pass there as a success. Absence of reported failure is absence of measurement.
3. **Three ideas transfer.** (a) Check the inputs the page actually holds against the facts code typed, before the calculation is submitted (structured read-back; both projects have a weak form of this; ours can be strong because code owns the facts). (b) Retry a failed *check* but never replay an *action* (Sentient's split), which is what our goal-drift layer lacks (see point 4). (c) Set a native drop-down by writing the chosen value onto the element through code, instead of operating its pop-up with clicks and Enter (Sentient's legacy design uses element value-writes; browser automation APIs do the same). Nothing from either project is shown to cure screenshot-only loops; the closest ideas are text state beside the screenshot and code-classified action effects, and the frame hint we already tried is a weak sibling of the second.
4. **The "false gate stop on a benign drop-down" is, by our own code, probably not a gate mis-classification.** The stop code `off_goal_unavailable` means the goal-check model call failed to run, and the layer then pauses by design; the gate itself said fill (section 6.2). The fix is a bounded retry of that check, not a change to the gate. This does not come from the references except as a pattern.
5. **Our "caught by code" for the wrong figure on B relies on the evaluation's oracle.** The product's own `check_completion` compares the case note against what the navigators read; it would not have caught a wrong but well-formed figure (section 6.3). Worth saying plainly before any claim.

**Is the task comparable to ours?** Ours is: a model drives three differently laid-out calculator web pages, in a headless browser, from screenshots, typing facts it is only allowed to name, through a deterministic gate, unattended, judged by a code oracle on 4 held-out households. Clicky's task (point at one element, once) is **not comparable**. Sentient's task (do a user-stated job on a real Mac with the user present) is **comparable in kind but not in conditions**: different surface (real Chrome or Safari through the OS accessibility layer versus headless Chromium through screenshots and a DOM read), a human who can press STOP or take over, no value-hiding rule, no deterministic action gate, and a success definition that is the model's own claim.

One honest nuance from Sentient's own legacy manual (`Driver/CuaDriverSkill.swift`, retained for cleanup only; the active path is the vendor helper): for **web text fields** the manual says the accessibility layer can echo a write the page never showed, the driver reports such writes as unverifiable, and the fallback is a real click then typing. So even the design that values accessibility actions concedes that browser form entry is the soft spot. It does recommend element-level actions for drop-downs and checkboxes in pages.

## 2. How do they target elements? (Q2)

**Clicky app.** Pixel coordinates in the screenshot the model saw, as one text tag at the end of the reply (one point per reply, an explicit "none" allowed). Screenshots are scaled so the long side is 1280 px; the app maps pixels to screen points. No verification of the point (`CompanionManager.swift` tag parser, about lines 782 to 823; `CompanionScreenCaptureUtility.swift` line 84). A dead file (`ElementLocationDetector.swift`) shows an earlier design: use a vendor computer-use tool only as a grounding step to get a coordinate, with the screenshot resized to the nearest recommended size that keeps the display's aspect ratio. **Clicky Windows fork.** Same coordinates, with a structured result carrying a confidence and an explicit no-point reason, and an evaluation made of real screenshots with allowed regions and distractor regions: a point counts only if it lands in the allowed region and outside every distractor; abstaining counts as acceptable where the target is ambiguous (`windows/docs/pointing-redesign.md`, `windows/tests/Clicky.Tests/Fixtures/pointing/`). Its executor clicks by coordinates with no check of what is under them.

**Sentient OS.**
- Accessibility-first. The model reads an app's state, which returns a text tree of elements plus a screenshot taken at the same moment, then acts on an element identifier from that read. Pixel coordinates are described as the fallback, used only on a real signal (the tree is empty, an action reports no effect, or the tree disagrees with the picture). Identifier binding to a specific read is described in the legacy manual (a newer read invalidates older element tokens). For the active vendor helper I cannot see how identifiers are bound; the helper is a closed binary and its tool schemas are fetched at runtime and are not in the repo.
- Drop-downs, checkboxes and sliders: the legacy manual teaches **writing the value onto the element** (replace the control's whole value) rather than opening the pop-up. For text typed into web pages it falls back to focus-by-click then typing (see section 1).
- Hidden fields and page state: nothing special that I found. Hidden elements are presumably absent from the tree (my inference about accessibility trees; I did not see it stated). The defences are procedural: re-read after any navigation, wait and re-read for loading screens (a bounded number of times), cross-check the tree against the picture because the tree can be wrong (for example virtualised rows with bogus geometry), and a sparse web tree on the first read often fills on a second read.

Compared with ours: we already do something stronger at the moment of action (the trusted DOM read of the element under the point, `tiers/computer_use.py` `read_target`; the gate classifies from that read, not from the model's words). What we lack is the other half: **a way to set a control without operating its pop-up**, and **a read of the control's value afterwards**.

## 3. How do they verify, and how do they stop false completion? (Q3)

**Clicky.** `hermes-clicky-plugin/post_action_verification.py` classifies a fresh observation as success, failed, uncertain, blocked by a prompt, or skipped, with blockers looked at before success, and "changed but unverified" as uncertain. **The observation flags (screen changed, matched expected state, error dialog visible, target unchanged, app lost focus) are supplied by the caller**, that is, by the same agent being checked (`hermes-clicky-plugin/tools.py`: the tool does not capture the screen; it accepts an already-collected observation from the caller). So it is a verdict vocabulary and a stop rule, not an independent check. We already lifted its shape and rebuilt the input side so that code reads the named fields (`vendor/clicky/clicky_lift/postcheck.py`). There is no completion check against a task result.

**Sentient OS.** Three layers, none of them a check of the result:
1. **Instructions to the model:** a tool call that succeeded does not prove the task succeeded; re-read fresh state and verify the requested result before claiming done; never repeat a change just because reading the result failed; after an uncertain action look at what happened before acting again (`Driver/OpenAIComputerUse.swift`, the rules block; read, not reproduced).
2. **Broker code:** a mutating action is refused unless the model has read that same app's state earlier in the task. From my reading of `NativeComputerUseServer.swift` the "has been read" mark is set by a successful state read and cleared by a failed call, a replayed or conflicting request, or a replaced session. **It is not cleared by a successful action**, so it enforces "you have looked at this app at least once since the last failure", which is weaker than "you looked after your last click". (The owner's prose study says "since the last failure or mutation"; the code I read does not clear on a successful mutation. Treat as my reading of one file.) Repeated requests are never executed twice: identical replays return the stored answer, a changed replay is an error. Actions are never retried by the broker; only state reads are retried, a few times, inside a shared deadline of about a minute and a half. A failed action's error tells the model that its effects may be unknown.
3. **Final status:** completion needs an explicit claim after a clean exit; a claim of failure beats a contradictory claim of done; no explicit claim is reported as unconfirmed, with advice to check the app before repeating (`Cloud/AgentStatus.swift`, the native doc).

The legacy driver adds the best idea in the area (design only): after each action, **poll a declared postcondition about named elements** (exists, value, enabled, selected), with results satisfied, unsatisfied or unknown, and **unknown never counts as success**; and each action returns a classified effect (confirmed with real read-back, unverifiable, partial, suspected no-op, refused) with a hint about what to try next.

**Would any of this stop our failure (a), a confident Done with a wrong figure?** No, not by itself. Sentient's "done" is the model's claim; its verification is a prompt. Ours is stronger already: code decides, and the figure is compared with an oracle in evaluation. The transferable part is **earlier and narrower**: read the inputs back before the figure exists.

## 5. Permission, confirmation, stopping (Q5)

- **Clicky plugin:** five tiers from observe to full control, default confirm-before-action, a request cannot raise the tier (`permission_policy.py`); a keyword policy; a confirmation state with expiry; an audit log; a scoped autopilot session (scope, step cap, timeout, stop on a failed verification, cancel). But the tool path that actually calls the bridge **hard-codes the permission and safety decisions as "allow"** and turns a model-supplied approval flag into an approved confirmation (`tools.py`, `execute_clicky_action`), so the policy modules are not enforced there. Details in `clicky-reuse.md`.
- **Sentient OS:** the user starts a task; one task at a time app-wide; STOP cancels the agent process and closes the helper connection; no per-action approval (the agent is launched with approvals and sandbox switched off, `Cloud/CodexCLI.swift`, and the README says the app does not ask for confirmation before each click); scope is by prompt, which Sentient's own security document describes as not a sandbox. Proactive computer tasks are **not** read-only: the executor fires one user-approved plan the same way, and its header comment says the prompt is the only safety layer there (`Proactive/ProactiveExecutor.swift`). (Correction to the owner's prose study, which says proactive runs never use computer use: the judge and research stages are read-only, but the executor can fire a computer task after the user's press.) Good small ideas: a question tool restricted to two answers, answerable only through the app's own UI; a diagnostic that needs a single-use consent that only a real UI answer can grant.
- **Ours:** deterministic gate on a trusted read of the target (`security/pipeline.py`, `gates.py`, `labels.py`), a goal-drift check and stuck detector (`security/drift.py`), an injection detector, denylist, kill file, signature-bound single-use approvals, a hash-chained audit. **Ours is much stricter than either, and the strictness has a price: pauses that are not about the step.** One of four held-out households was lost to one (section 6.2: a goal-check call that failed, not a bad step). Neither reference gates the way we do, so neither tells us how to tune a gate; the only transferable pattern is Sentient's split between retrying reads and never replaying actions.

## 6. What our own code and result files say (so adaptations match causes)

### 6.1 The facts

From `evals/agentic/results/heldout_clean_9137.json` and `ITERATIONS.md` (gate `35e964049fd0`, gpt-5.5, n = 4, descriptive only): 1 of 4 completed; hh_0002 and hh_0003 finished with a claim of success and a wrong figure on B (A and C matched); hh_0001 was paused by the goal-check layer (section 6.2) on a key press; in all four the designed Submit waited for a human. No per-step trace was kept, so nothing in the stored files shows what was typed where.

### 6.2 The false stop (b): what the code says it was

The stop record says: layer **drift**, code **off_goal_unavailable**, nav-c step 25, kind **key**, role combobox, label "Show my results", structure submit-control plus a results path, gate classes **fill** only (`evals/agentic/results/heldout_clean_9137.json`, hh_0001 `gate_stops`).

- In `services/agent/understudy_agent/security/drift.py`, the source "unavailable" has exactly one origin: the goal-check model call raised a provider error or returned an invalid answer, and the layer then pauses "to be safe". It is a fail-closed pause, not a verdict that the step was off goal.
- In `security/pipeline.py`, every step kind that is not on the short benign list (typing, filling, selecting, screenshots, scrolls and waits are on it; **clicks, key presses and drags are not**) gets one such model call. A household is 78 to 117 steps across three navigators running at once, and every click and key press among them is one such call (tens per household, several in flight at a time). **One failed call ends that navigator, and through cancellation the whole household** (the other two navigators in hh_0001 ended with a cancel error). There is no retry.
- The stored file keeps no error class, so I cannot say whether it was a rate limit, a timeout or an invalid answer.
- So the working description in `ITERATIONS.md` (the gate read the native select as a submit control) puts the cause in the structure read, but the stop code is the goal-check failure. The structure fields in the record only describe the target. The same holds for the Gemini smoke (iteration 5): its stop on the 14th click was the repeat detector acting on 13 identical clicks, which is the detector working, not a mis-classification.
- A separate and smaller observation from reading the trusted read in `tiers/computer_use.py`: for a key press with a drop-down focused, the read describes the target as the form's default submit button (it treats the drop-down like a text box, where Enter submits). The gate verdict here was fill, so it did not cause this stop, but it feeds a misleading description to the goal-check model. Low priority.

### 6.3 What our "code check" is, and is not

`services/agent/understudy_agent/completion.py` `check_completion` requires the saved case note to contain each calculator's amount, status and reference **as the navigators read them**, and the note id. `navigator.py` `_tier3` `verify` only requires that the page "looks final" and parses. Neither compares the figure with what the household's facts should produce. In the held-out round, the wrong figures were caught by `live_t3.py`, which compares each figure with the sandbox oracle (`sandbox_sites/oracle.py`). So: **in the harness the wrong figures were caught by an oracle; in the product, with real households and no oracle, the same run would have passed as done.** The input side is different: code knows every fact it typed, so code can check what the page holds (6.5).

### 6.4 Native drop-downs

Site B has four drop-downs on one page, the first control being "Adults in household". The Gemini smoke ran 13 clicks on one drop-down and typed nothing (`ITERATIONS.md`, iteration 5, which notes a headless screenshot cannot show a native pop-up open). With synthetic mouse input over the browser debugging protocol, clicks aimed at a native pop-up's option positions are not delivered to the pop-up; they land on the page underneath. This is a well-known limit of browser automation, which is why those tools provide a dedicated select call. I did not test it here. It explains, as one candidate, the 13-click loop, the model pressing keys on a drop-down, and a drop-down left at its default.

### 6.5 Calculator B's wrong figures: what is known

- The two failing households need non-default drop-down values (couple with bedrooms 3; lone parent with bedrooms 2); the one household that passed on B has every drop-down at its default (checked by generating the households from the seed; read-only call).
- **But** the dev households of the same archetypes have the same drop-down values (couple, bedrooms 3; lone parent, bedrooms 2) and B passed for them. So the drop-down explanation alone does not separate dev from held-out. Other candidates: a handle typed into a neighbouring field, a stale value left in a field, a different number format in the held-out values, or the reference and figure being read from the wrong place on the page.
- **Undiagnosed.** The cheapest discriminator is a typed-input read-back with a record of (handle, field role, match yes/no) per step. No stored trace has it.

### 6.6 Screenshot-only loops (c)

Seen on site b at step 4 in a dev run and in the hint-on pre-flight (n = 1 each), and as 13 clicks on a drop-down with Gemini. The notes do not say which control the step-4 loops were on, so linking them to the drop-down is a hypothesis to check from the next traces. Neither reference documents or solves this failure.

### A1 Typed-input read-back and pre-submit audit

*The idea.* Code owns the facts and resolves each handle to a value at the moment of typing, so code knows what every field ought to hold. After each typed fact, and again immediately before the click that submits the calculation, trusted code reads every control in the form (name, accessible label, type, current value; for drop-downs, the selected option) from the DOM, including controls in a hidden panel and hidden carried fields, and compares the set of values with the set of values code typed. It records, per step and with no value: the handle name, the field's role, and a yes or no. A mismatch (a value missing, duplicated, or in a field whose label does not suit the handle) stops the submit click with a code-written message that names the handle and the field label class, never the value, and the loop re-enters the field. `done` for a navigator requires the final audit to be clean. This is the same pattern as Clicky's post-action verification (a declared condition checked after an action, blockers first, unknown means stop) with the input read by code instead of supplied by the caller, and the same pattern as Sentient's legacy driver, which polls a declared postcondition on named elements and never counts an unknown result as success.
*Expected effect.* Catches lost, duplicated and overwritten values and drop-downs left at defaults, whichever mechanism caused B's failures, and makes the cause visible in the trace. It will not catch two values swapped between two fields of the same kind, unless a label-to-handle binding exists (a later step; lexical binding is brittle and should only ever mean "uncertain, ask").
*Risks.* Number formats (commas, trailing zeros) need a normalised comparison. Fields cleared by page scripts on re-render. Reading values touches sensitive-field rules: compare in memory, keep only the booleans, and never read a field listed in `packages/schema/sensitive_fields.json`. Labels are page text: pass them through the sanitiser and keep only a class.
*Test.* Offline against the three sandbox sites with a deliberately mis-typing fake model (wrong field, skipped field, drop-down left at default); then one live calculator B run, with a stored per-step audit record.

### A2 Retry the goal check, never the action

*The idea.* A model check that fails to run is not evidence that the step is off goal. Sentient's broker retries its state reads a few times with growing waits inside one shared deadline, and never replays an action; the same split applies here. The goal check is a read, so retry it a bounded number of times (for example twice, short waits, one overall deadline), then fail closed exactly as today. Never retry when the kill flag, the budget guard or a pause says stop. Write the error class (rate limit, timeout, invalid answer, other) as a token into the audit and the result row, so the next round can tell which it was. Do not retry the action itself.
*Expected effect.* Removes the pause that cost hh_0001 if its cause was transient. Adds latency only on failures. **Held-out discipline:** seeds 9137 and 9138 are used up; any fix needs new seeds and a new pre-registered round.
*Risks.* Low; the layer still fails closed after the retries. Later option, only after measuring: skip the model check for kinds the gate already classes as plain read or fill on a non-outward target. That changes the security layering, so it is not part of this item.
*Also noted (low priority).* In the trusted read, a key press with a drop-down focused is described as a press on the form's default submit button. Excluding drop-downs from that rule, or refusing keys on a focused drop-down with a code-written message, would stop feeding the goal check a misleading description. Confirm in our browser that Enter on a focused closed drop-down does not submit the form before loosening anything; if unsure, take the refusal route.

### A3 Set a drop-down by fact, through code

*The idea.* The model chooses the control as it does now (a click on the select, verified by the trusted read), and then names a handle. Code sets that select to the option whose text or value matches the resolved fact, through the page's own select mechanism, on the element the trusted read identified. No clicks at pop-up option positions, no Enter. The gate classes the action as fill; the pipeline authorises it like typing. The same primitive can later serve text fields. Sentient's legacy design writes values onto elements for drop-downs, and our own tier-2 already has the verb (`tiers/browser_agent.py` and `tiers/dsl.py` call a select-option routine; `security/gates.py` classes it as fill).
*Expected effect.* Removes the likely cause of the 13-click loop and of a drop-down left unset or set by blind key presses. A plausible contributor to (a) and (c); **not** a fix for the false stop as it occurred (section 6.2).
*Risks.* A new write path through the gate; it must go through `pipeline.authorise` with a target read and a closed vocabulary (handle only, never model text). Custom drop-downs built from ordinary elements (a listbox) are not covered. **Unverified:** whether the OpenAI computer tool call path in `models/openai_provider.py` allows a second function tool beside the computer tool; if not, the action must be expressed another way (for example a typed handle into the focused select, with code choosing the option). Check before estimating beyond 8 hours. Prove the premise first with a 30-minute offline test with no model: on sandbox site B, open a drop-down with the real actuator, take a screenshot (is the pop-up in it?), click where an option would be, and read the DOM (did the selection change, or did the click land on the control underneath?). If the click does change the selection, drop A3.

### A4 Click-accuracy fixtures

*The idea.* Clicky's fork scores a pointing answer against hand-drawn allowed regions and distractor regions, and counts abstaining as acceptable when the target is ambiguous. Our sandbox pages give the allowed region (the target element's box) and the distractors (neighbouring controls) from the DOM for free. Record frames once, ask the model for the click for each, and report on-target rate with a Wilson interval, split by control kind (text field, drop-down, button). Static frames cannot show a pop-up, so this measures only where the model aims in the closed state (the drop-down itself, the field, the button). It would show whether wrong-target clicks are a real share of the failures before anything is built, without a household run. It does not test the pop-up premise behind A3; the 30-minute test there does.
*Risks.* A few model calls (small cost). Frames are evidence screenshots of pages an agent operates, within D37.

### A5 Code-written effect line per step

*The idea.* After each action, send the model one code-written sentence built from tokens: whether the screen changed, the role and label class the trusted read found, whether the gate refused, and the step count. Both references classify action effects in code (Clicky: target unchanged, screen unchanged, error dialog; Sentient legacy: confirmed, unverifiable, suspected no-op). We already tried a lighter form (the frame hint) and it coincided with a stuck loop once; the n = 1 result cannot separate the hint from the model's own quirk. So test it, do not ship it.

### A6 Text control list

Sentient's native route returns text and picture from the same instant, and its manual says text alone often suffices. For us this puts page-controlled text into the action model's prompt; the reader quarantine exists to prevent that. If ever adopted: only through `security/sanitize.py` and the detector, as data, and with labels reduced to a role and a closed word class. Not recommended before the deadline.

### Already have (no work)

Step caps and deadlines; stateless context; a stuck detector; code-decided completion; per-child leases (`vendor/clicky/clicky_lift/lease.py`, planned for BGA-1); signature-bound approvals and a hash-chained audit (stronger than Clicky's confirmation state and audit log); the drift layer (a model-based goal check that I did not find in Sentient). Sentient's "ask with two choices" is what our approval card already is.

## 8. What we should NOT adopt

1. **Clicky's bridge as written** (the unsafe items in `clicky-reuse.md`): a shell-invoked command taken from an environment variable; hard-coded allow decisions and a model-supplied approval flag; unescaped text in AppleScript key code; bundled analytics that sends transcripts.
2. **Verification flags supplied by the agent being verified.** Clicky's tool takes "matched expected state" from the caller. Any observation used as evidence must be read by code.
3. **Coordinate clicks with no read of what is under them** (both Clicky executors). Ours reads the element first; keep that.
4. **Substring safety words** (noted before): they fire inside ordinary words and scan the model's own rationale.
5. **Approvals off as the trust model** (Sentient launches its agent with approvals and sandbox off, including for proactive computer tasks, with prompts as the only guard). It conflicts with "the model proposes, code decides".
6. **No step, time or request ceiling** and **no termination policy** (Sentient leaves recovery to the model). We need caps for cost, held-out budget and unattended safety.
7. **"Done" as the model's claim after a clean exit** as the success definition.
8. **Raw page or accessibility text in the action model's prompt** without the sanitiser and detector (A6), as Sentient does with prompt-level separation only.
9. **The vendor-signed helper app and its download-at-runtime path**, and the Codex CLI as our loop: closed, macOS-only, not usable on a headless sandbox, and not a reference we may copy.
10. **Telemetry** (Sentient's error and usage reporting; Clicky's PostHog and form posts) and all bundled upstream signing, update and media.
11. **Any Sentient code or prompt text** (AGPL-3.0). This note is the only thing an implementer may use.

## 9. Verdict: does their approach face our problems?

- **Clicky: no, because its task is different.** The app never acts; the plugin acts once per request from outside, with no loop. Where it does face a hard version of our grounding problem (pointing at the right element from a screenshot), its fork's own notes call it unsolved and respond by abstaining and by testing against distractors. That is a measurement idea for us (A4), not a fix.
- **Sentient OS: it faces the same class of problem but does not show that it solves it.** The loop and context handling are not in the repo, the actuator is closed, and success is the model's claim. The design choices that matter (element-level actions and value writes, text state beside the picture, read before write, never replay an action, classify effects) are sound ideas. They are **plausible fixes for a cause behind (a) and (c)**, and the retry-the-check, never-the-action split fits (b). None is shown by the reference to work on web forms in a headless browser.
- **The owner's belief is therefore best stated as: "Sentient probably meets our native-drop-down problem less often because it acts on elements rather than clicking pop-ups; this is a design inference, not a measured result, and the task and success definition differ." It does not touch (b) as it occurred, which was our own goal-check layer failing closed, and it cannot touch (a), where our oracle is the stronger instrument.**
