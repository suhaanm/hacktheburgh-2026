**The order is the point.** A quantitative judge distrusts a cut that opens with a win. This one opens with where the model fails and the guard that catches it, then the win with its limits, then the mechanism that makes the win checkable.

**Where.** Knack, Admin view, More, Evidence (a reviewer's row, not a worker screen). The blocks are "Does it hold out of time?" and "Does the rule beat the naive one?". Take it with the engine answering, or in the example view, which reads the same report. H4 uses a terminal, so have `make hrt-proof` ready in a second pane (it takes about five seconds, calls no model and no network).

**The one-line live proof (H4).** `make hrt-proof` (or `uv run --package understudy-engine python scripts/hrt_ledger_proof.py --wait 2`) prints: the forecast with its time, the model's and the base rate's probabilities and its hash, marked "outcome: not yet known"; two seconds later the outcome with its hash chained to the first; one forecast's log loss beside the base rate's, marked as mechanism and not evidence; the chain verified; an edit of the old forecast refused; a second outcome for the same forecast refused. The forecasted bin is picked by position, never by how it turns out, so the forecast can be wrong; it prints either way (`--seed` picks another generated person). Generated data, a small model fitted on four generated people, no model call, no network (C104).

**The data pipeline in 15 seconds, if a judge asks** (C105; the full paragraph is `docs/HRT_BRIEF.md` section 1b): "Level-0 events only, no text, no URLs, no field values. Features use only what had happened by that moment, and a test truncates the future to prove it. Each model is fitted once and frozen. The forecast goes into a hash-chained ledger before the outcome exists, and we score from the ledger. A threshold and a guard, which are code, make the decision. The ledger holds a salted hash, a number and a label, never text, and none of it leaves the device. All of it here ran on generated events, none on real workers."

**Do not say.** That the stuck model "works" or "generalises": scored forward in time on other generators it is worse than the best naive predictor (C93). That any of this is measured on people (it is not; C70). That four wins of four is evidence the rules are good (C96). That the ranges are "calibrated": they cover as promised only where they were calibrated, and recalibrating them restores the stuck-set coverage by making the set hold both labels in most origins (C101). That the net minutes are measured: the cost of an interruption is our assumption, and in the shifted worlds interrupting at every origin beats the model (C102). That the guard is clever: in decision terms it stops the damage of a model worse than a one-line baseline.

**If it fails.** The blocks are `pending` until `evals/report.json` carries the `hrt_ledger` and `hrt_decisions` sections (`python -m understudy_engine.eval --merge --only hrt_ledger,hrt_decisions`, then `node apps/dashboard/scripts/sync-eval-fixture.mjs` for the offline fixture); a pending block says why in one line. Never show the dev result: `evals/hrt/results/dev_*.json` is for debugging only and is never read by the report.
