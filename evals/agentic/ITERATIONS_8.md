## Item 1: bounded retry of the goal check, error class recorded

**What.** `security/drift.py` `DriftChecker.check` retries a check that fails to RUN, at most 2 times (so at most 3 calls per check), with fixed waits of 0.5 s and 1.5 s (no jitter), inside a 45 s budget measured by an injectable clock (no retry is started when the time so far plus the next wait would pass it), and looks at the kill flag (`should_stop`, wired by `security/pipeline.py` to `is_killed`) before every wait and every retry. When every try fails the layer fails closed exactly as before: `off_goal_unavailable`, a queue item, a pause.

**What is retried and what never is.**
- Retried: a rate limit, a timeout, a transport error, an answer the layer cannot use (not an object, or no boolean `serves_goal`), an unclassified provider error.
- Not retried: a `ModelRefusal` (its own docstring says not to), a permanent 4xx (a refused key, a malformed request; 409 excepted), a provider `kind` of `auth` or `blocked`.
- Never asked again: an answer of `serves_goal = false`. A negative verdict is final; the layer does not re-roll it.
- Never touched: the action. `check` is the only port method the drift layer calls (the test double fails the test if `plan`, `read`, `vision` or `computer_step` is reached), the pipeline authorises the action once after the check (`pipe.budget.steps == 1`), and in the real tier-3 loop the click is performed once, the model is asked once for that step, and no step is spent.
- A `BudgetExceeded` from the live harness's spend guard (not a provider or value error) is not caught and so is never retried.

**Error class.** Closed enum `CHECK_ERROR_CLASSES = (rate_limit, timeout, invalid_answer, transport, other)`, decided from the exception's `kind` (Gemini), an HTTP status, the class names along its MRO and its cause chain, builtin families, and the class-name prefix the OpenAI provider puts on its messages (`RateLimitError: ...`). **The text of a message decides nothing** (a message that merely talks about rate limits is `other`). Recorded in: the verdict (`error_class`, `attempts`); the `StepDecision` (`check_error`, `check_attempts`, set only when the check could not run); the `drift_pause` audit line (`check_error`, `attempts` as tokens); a new `drift_check` audit line (`recovered` or `failed`, with the class and the attempt count) whenever at least one try failed, so a failure that a retry masked is still counted; the gate-stop row of the live harness (`check_error`, `check_attempts`); and per run in `goal_checks` (`checks`, `retried`, `recovered`, `failed`, failures by class). No message text is kept anywhere.

**Tests (offline, hermetic, injected clock and sleeper, fake port).** `tests/safety/test_drift_retry.py` (62): classification for each class from each exception shape; transient failure of each class then success; all tries failing for each class; the fixed waits; refusal and permanent errors not retried; a negative verdict asked once; unusable answers retried; the total-time bound; the stop signal; a configuration error not swallowed; counters; the pipeline (audit lines are tokens only, `pipe.budget.steps`, the kill flag set during the first failure ends the retries); the gate-stop row. `tests/core/test_cu_goal_check_retry.py` (3): in the real `ComputerUse` loop a check that fails twice then answers leaves the click performed once and the model asked once for that step; a check that always fails leaves the actuator untouched and a gate-stop row with `check_error: timeout`; a negative verdict is one call. `tests/safety/test_drift.py` (existing) updated only to inject a no-op sleeper.

**What this does not show.** The probable cause of the hh_0001 pause was the local length cap, which Item 0 removes. The retry covers the other, transient causes. Which of the two mattered in a live round is not known until the next round records the class.

**Costs and side effects, stated.** The retry adds no model call on a clean check. On a failing check it adds up to two calls and up to 2 s of waiting. **`authorise` is synchronous and is called inside the async tier-3 loop, so those waits block the event loop of the whole run (all three navigators)**; the bound is 2 s per failed check, plus the calls themselves. A provider call that itself retries inside the SDK can take much longer before it fails; the 45 s budget stops further retries after one such call.

## Item 2: typed-input read-back, pending-handles guard and pre-submit audit (`tiers/form_audit.py`)

**Mechanism (all code, no model).**
1. **Read-back after each typed handle.** A page script in the same isolated CDP world as the target read looks at the FOCUSED control and says whether it now holds the value just typed: `landed` yes, no or unreadable; the focus kind (input, select, textarea, document, other); the control's role; the page's own id for it as a short token; a position among the page's controls. **The comparison runs inside the page script: the expected value goes in as an argument and only enums, a token and a number come back. A control's value is never returned to Python, printed, logged or stored.** Fields in `packages/schema/sensitive_fields.json` are never read (the policy is passed into the script; they come back `unreadable: sensitive`). Formatting differences are not mismatches (`6,000` and `6000`, `£6000`, `3, 7` and `3,7`, case, spaces). Reasons: `no_focus`, `not_a_field`, `empty`, `mismatch`, `appended`, `select_unmatched`, `wrong_field`, `sensitive`, `disabled`.
2. **If it did not land**, the handle stays pending, the step is recorded `ok = false (not_landed)`, and the next prompt carries a code-written note naming the handle and a closed reason (never a value, never page text) and telling the model how to retry. Three failures on one handle stop the attempt (the ladder restarts once on a fresh page, then a human).
3. **Binding.** A handle that landed is bound (in memory only) to the control that took it.
4. **Pending-handles guard and pre-submit audit on the FINAL button** (its name comes from the site spec: `Calculate`, `Work it out`, `Get my estimate`, `Show my results`, `See entitlement`; `Save draft` for the case note; also Enter in a field whose default button it is). Before that click goes to the gate, code re-reads every bound control (hidden carried fields and fields of a hidden panel included) and compares each with the fact it should hold; a handle never entered is `not_entered`. Anything not clean **holds the click** and tells the navigator which handle ids and why. At most 3 holds per page, then the attempt stops. A control that cannot be read (vanished, ambiguous, sensitive, opaque) makes the audit `uncertain`: the click is held and a human is asked at once, with no second try. Optional strictness for the sandbox jobs: text left in a text-like control that no fact was entered in (`stray_value`).
5. **Done.** The loop only accepts a claim of success when the latest pre-submit audit was clean; otherwise the outcome is `claimed_not_verified` and it is counted as a false claim (never hidden).
6. **The product, not only the oracle.** `completion.check_completion` takes the form audit's verdict per calculator and treats anything but `clean` or `n/a` (not tier 3, or a checkpoint restore) as missing: `calculator b: inputs not verified (mismatch)`. The orchestrator's verifier refuses a result whose navigator did not have a clean audit even when the fresh re-read matches the figure. The goal text is not touched.

**Per-step enum records (so the mechanism is visible next time).** Step events carry `focus=`, `field=` (the page's own control id as a token, digit runs masked), `landed=`, `reason=` for typed handles; `role=`, `field=` for clicks; `keys=` (a closed set of named keys; a letter is recorded as `other`) for key presses. The audit log gets one `form_audit` line per record (`readback:household.bedrooms:select_unmatched`). `t3_runs` in the result file carry `inputs`, `form_audit` (state, audits, blocks, read-backs by result, pending handles, up to 80 records of handle id, role, match, reason) and `readback_failures`. No value is in any of them (a test over prompts, events, audit lines, result records and the queue checks every household value of length 4 or more).

**What the offline reproduction shows** (`tests/core/test_live_t3_report.py::test_the_three_arms_on_the_held_out_mistake`: the same walked-past bedrooms drop-down on calculator B, a scripted double, three arms of `UNDERSTUDY_FORM_AUDIT`):

| `off` (typing as at the first held-out round) | run done, no audit | **no** (bedrooms 1): the held-out failure, reproduced |

**Limits, stated plainly.**
- **A wizard page cannot be fixed from the final page.** On site A a drop-down walked past on page 3 was only noticed at the final button on page 4, where no field for it exists (offline: 4 holds, a stop, a fresh page, about 35 extra steps; live, Gemini dev round 2 hh_0003: 3 holds and a stuck loop). **Built after that evidence (commit `c6de04e`): a page-scoped guard on the buttons that move on** (`Continue`, `Next`, site C's `Next: your money` and `Continue to finances`): the press is held while a handle whose control is ON SCREEN on this page (the page's own ids for it, from the job's `field_hints`; a hidden panel does not count) is not entered, or while a handle bound on this page no longer holds its fact; the note names the handle ids and a closed reason. Same cap as the final button (3 holds per page, then a stop and a fresh page). It changes no final state and asks no human; it only needs the sandbox's field hints (a real site has none, so there only the final guard applies). Tests: a skipped age on page one of site A and on panel one of site C are held and fixed on that page with the site asked once with the right form; a clean entry has no hold (hidden panel two is not asked for); the read-back arm has no forward guard.
- The pre-submit audit reads what the DOM says. A hostile page can make its DOM say anything; this is a correctness check for honest pages, not a security layer.
- Without `field_hints` (the page's own ids per handle; only the sandbox sites have them) two values swapped between two fields of one kind are not caught by value comparison alone.
- A carried hidden copy of a drop-down holds the option VALUE, while the fact is the option TEXT; the two are equal ignoring case on site A, so no false hold arises there, but a real wizard could produce one. A false hold is bounded (3 holds, then stop) and fails toward a human.
- The audit is only used when the actuator can read the page's controls (the headless page actuator). The desktop and simulated actuators run exactly as before.
- Adds no model call. Adds about one CDP round trip per typed handle and one per final click.

## Item 3 (as briefed): set a native drop-down by fact through code. Not built, with the reason

The premise was tested with no model (`tests/core/test_select_popup_premise.py`, 5 tests, headless Chromium, the real actuator, site B on a private port). In the installed Chromium: a click on a native drop-down draws nothing in a headless frame; a click aimed where an option would be does **not** select it (it lands on the page underneath: the active element changes, the selection does not); arrow keys and Enter on a click-opened drop-down do **not** commit; but **typing the option text commits at once**, with or without a click first, and Tab only moves on. So blind clicks and key presses at a pop-up cannot work (which fits the 13-click Gemini loop), and the typed-handle route the loop already uses does work.

Decision: **do not add a write-by-code action.** (a) The diagnosis found the drop-down failures were omission and a possible later change, not a typing route that cannot commit; the read-back and the final-button guard now see both. (b) A new action kind is a new write path through the gate and the provider tool schemas (and whether the OpenAI computer tool path accepts a second function tool beside it is unverified), for no gain in mechanism over typing. (c) The Gemini stall is a prompt-fit failure on a frozen goal text. If a later round shows drop-downs still failing after typing lands, this is the next candidate, with the pop-up facts above as its premise.
